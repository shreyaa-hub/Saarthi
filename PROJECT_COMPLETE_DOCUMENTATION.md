## 1. Project Overview

### What this project does
Verbal Coach is a **teletherapy authoring and delivery platform for speech-and-language therapy** (and adjacent domains: articulation, language, fluency, social/pragmatics, cognitive, OT/fine-motor, behavioral). A clinician builds interactive therapy activities on a drag-and-drop **canvas** (like slide-authoring software), assigns them to patients, and monitors progress. Patients (often children) complete the activities in a focused full-screen **player** that auto-scores their work. Parents/guardians get their own linked view of a child’s progress and can send home-practice worksheets. An optional **AI insights** feature summarizes a patient’s recent attempts for the clinician.

### Why it exists
It replaces the paper worksheets, flashcards, and physical manipulatives a speech therapist normally uses in a session with authorable, assignable, auto-markable digital equivalents — while preserving the honest clinical signal (partial credit, “not scored” for open tasks, per-question review). It was built as a university capstone / internship project (contributors are listed in `README.md`).

### Main problem it solves
Therapy activities are hard to build digitally, hard to assign at scale, and hard to measure. This app gives a clinician one place to **author once, assign to many (or repeat across a week), and see accuracy trends and goal progress** without trusting the patient’s browser to report the score.

### Target users
Three first-class roles, each with its own route shell:
- **Clinician** — authors templates, manages a caseload, assigns work, reviews attempts, sets goals, bills guardians, messages patients/parents.
- **Patient** — completes assigned activities, sees streaks and progress.
- **Parent / Guardian** — linked to a child via a clinician-issued **guardian code**, sees the child’s progress, assigns/sends home-practice worksheets, messages the clinician, views billing statements.

There is also a **logged-out visitor**: the public marketing site, the browsable Global Library, and a “Try the Studio” experience that needs no account.

### Main features
- Canvas **Template Studio** with ~44 element types (see §8/§10): ~24 interactive/scored types + static “worksheet” furniture + basic content elements.
- **Server-side scoring** with item-level partial credit.
- **Assignment** flow with a frozen canvas snapshot, bulk assign, and recurring (repeat-over-N-days) assignment.
- **Patient player** (full-screen, responsive, read-aloud, auto-score, one-attempt-per-assignment).
- **Per-question attempt review** for clinician and guardian (including replaying saved drawings).
- **Analytics**: accuracy over time, per-domain breakdown, caseload “Clinical Pulse”, rankings, patient status classification.
- **Patient goals** (target accuracy over a window of attempts).
- **AI insights** (Anthropic Claude) and **AI worksheet generator** (clinician-only).
- **Messaging** (Supabase Realtime) — clinician↔patient and clinician↔parent, kept separate.
- **Notifications** (“Alert Hub”).
- **Global Library** (publish/import templates and assets, public browsing).
- **Printable/PDF** worksheet + report export.
- **Parent area**: guardian link, missions, progress, calendar, finances (record only), creator hub.
- **Guest “Try” Studio** with localStorage draft claimed on sign-up.
- **Billing/invoices** (bookkeeping only — no payment processing).
- **Blueprint rules** (shared authoring standards).

The `README.md` still documents only migrations 0001–0006 (it is out of date; 0007–0013 exist and are described in §8). ## 2. Project Architecture

### High-level architecture
A single **Next.js 16 App Router** application (server + client components + server actions + route handlers + a proxy/middleware), talking to **Supabase** (Postgres + Auth + Storage + Realtime) with **Row Level Security (RLS) as the real security boundary**, plus the **Anthropic API** for two optional AI features. There is no separate backend service — the “backend” is Next.js server actions / route handlers and, crucially, the Postgres RLS policies and `SECURITY DEFINER` functions.

```
                          ┌──────────────────────────────────────────────┐
        Browser           │              Next.js 16 (App Router)          │
  ┌───────────────┐       │                                              │
  │ React 19 UI   │  RSC  │  Server Components (data/*.ts read queries)  │
  │ client comps  │◄─────►│  Server Actions   (lib/actions/*.ts writes)  │
  │ zustand store │ fetch │  Route Handlers   (app/api/ai/*, auth/confirm)│
  │ (canvas edit) │ /POST │  proxy.ts (session refresh + auth gate)      │
  └──────┬────────┘       └───────────────┬──────────────────────────────┘
         │  Realtime WS                    │ @supabase/ssr (cookies)
         │  (messages,                     │ createServerClient / createBrowserClient
         │   notifications)                ▼
         │                     ┌────────────────────────────────────────┐
         └────────────────────►│               Supabase                  │
                               │  Postgres (RLS + SECURITY DEFINER fns)  │
                               │  Auth (email/password, JWT, bcrypt)     │
                               │  Storage bucket "template-assets"       │
                               │  Realtime publication supabase_realtime │
                               └────────────────────────────────────────┘
                                                 ▲
                    ANTHROPIC_API_KEY            │ (server-only)
   ┌──────────────────────────┐                 │
   │ Anthropic Claude API     │◄────────────────┘  (AI insights + worksheet gen)
   └──────────────────────────┘
```

### Frontend
- **React 19.2** + **Next.js 16.2.10 App Router**. Server Components fetch data through `src/lib/data/*`; client components (`"use client"`) handle interactivity.
- **Tailwind CSS v4** (via `@tailwindcss/postcss`), design tokens in `src/app/globals.css`, light/dark theme driven by a class on `<html>` set by an inline blocking script (`src/lib/theme.ts`).
- **Radix UI** primitives wrapped in `src/components/ui/*` (button, dialog, select, tabs, tooltip, etc.).
- **zustand** (vanilla store) for the canvas editor’s state, undo/redo, pages.
- **@dnd-kit** for drag-and-drop (palette→canvas, and interactive drag activities).
- **Recharts** for progress/trend charts.
- **framer-motion** for marketing/motion components.
- **sonner** for toasts; **lucide-react** for icons; **react-hook-form** + **zod** available for forms.

### Backend
No standalone server. The backend surface is:
- **Server Actions** (`"use server"`) in `src/lib/actions/*` — all mutations (auth, templates, assignments, attempts, messages, goals, billing, library, parent, notifications).
- **Route Handlers** in `src/app/api/ai/*` (POST) and `src/app/auth/confirm/route.ts` (GET).
- **`src/proxy.ts`** — Next.js 16’s renamed middleware (see §5), which refreshes the Supabase session and gates role routes.
- **Postgres** is where authorization actually lives: RLS policies + `SECURITY DEFINER` RPC functions.

### Database
**Supabase Postgres.** ~17 application tables, extensive RLS, several `SECURITY DEFINER` functions and triggers. Canvas documents stored as `jsonb`. See §8 for the full schema.

### APIs
- Internal REST-ish route handlers: `POST /api/ai/insights`, `POST /api/ai/worksheet`, `GET /auth/confirm`.
- Everything else is **server actions** (RPC-style, not addressable URLs) and **PostgREST** (Supabase auto-generated REST used by the JS client under the hood).

### External services
- **Supabase** (Postgres/Auth/Storage/Realtime).
- **Anthropic Claude** (`@anthropic-ai/sdk`) — optional.
- Google Fonts (Plus Jakarta Sans, JetBrains Mono, Fraunces) via `next/font/google`.

### Authentication
Supabase Auth, email/password, JWT session in cookies via `@supabase/ssr`. Roles stored in `profiles.role` (source of truth) and mirrored into JWT metadata (best-effort). See §9.

### Storage
Supabase Storage bucket **`template-assets`** (public read, owner-scoped writes keyed on `<user_id>/<file>` path). Created in migration 0001.

### Background jobs
**None.** A deliberate design decision: recurring assignments are *materialized at assign time* (all rows created up front) rather than expanded later by a scheduler (see `src/lib/actions/assignments.ts`).

### AI/ML components
Two server-side Claude calls: progress **insights** (`src/lib/ai/insights.ts`) and **worksheet generation** (`src/lib/ai/worksheet.ts`). Both parse JSON out of the model response defensively. Model defaults to `claude-sonnet-5`, overridable via `ANTHROPIC_MODEL`.

### Third-party integrations
Anthropic only (plus Supabase, which is the platform). No analytics/telemetry SDKs, no payment processor.

### How components communicate
- Browser → Next server: RSC render + server action POSTs + a few `fetch()` calls to `/api/ai/*`.
- Next server → Supabase: `@supabase/ssr` server client using the caller’s cookies (so RLS applies as that user).
- Browser → Supabase Realtime: direct WebSocket subscription (browser client) for `messages` and `notifications`.
- Next server → Anthropic: server-only, key never exposed to client.

## 5. Application Entry Points

### Where the application starts
There is **no single `main()`** — it’s Next.js. Practical entry points:
1. **`src/app/layout.tsx`** (Root Layout) — the top of every page render. Loads three Google fonts, injects the **blocking theme script** (`THEME_INIT_SCRIPT`) into `<head>` so the correct light/dark class is set before first paint (no flash), sets `<html>`/`<body>` classes, and mounts the `<Toaster/>`.
2. **`src/proxy.ts`** — runs on (almost) every request before the route renders. Its `config.matcher` excludes `_next/static`, `_next/image`, `favicon.ico`, and image files. It calls `updateSession()`.
3. **`passenger-server.js`** — only when deployed via cPanel/Passenger; boots Next programmatically (`next({dev:false})` + `http.createServer(handle)`), listening on `process.env.PORT || 3000`. On Vercel this file is unused (`next start` equivalent is managed).

### Startup / per-request flow (proxy → page)
Trace for a protected route (e.g. `/clinician`):
1. Request hits **`proxy.ts` → `updateSession(request)`** (`src/lib/supabase/middleware.ts`).
2. If `NEXT_PUBLIC_SUPABASE_URL`/`ANON_KEY` are **missing**, it lets the request through (so the marketing site still renders instead of crashing).
3. Builds a `createServerClient` bound to request cookies; calls `supabase.auth.getUser()` (this refreshes the session and writes refreshed cookies onto the response).
4. Computes `isRoleRoute` (path starts with `/clinician`, `/patient`, or `/parent` — from `ROLE_ROUTE_PREFIXES`) and `isAuthRoute` (`/sign-in`, `/sign-up`, `/forgot-password`).
5. **Not signed in + role route** → redirect to `/sign-in?redirect=<path>`.
6. **Signed in + auth route** → redirect to `homeForRole(jwt role)` (best-effort; the destination page re-checks).
7. **Deliberately no role-vs-route gating in the proxy** (comment explains this prevents an infinite redirect loop between the JWT role claim and the DB role). The proxy only gates “authenticated or not”.
8. Any exception is caught and the request is let through (a proxy crash would take down the whole site; pages still enforce auth themselves).
9. The **page/layout** renders. Protected layouts call **`requireProfile(role?)`** (`src/lib/auth/session.ts`), which is the single source of truth: it fetches the `profiles` row, redirects to `/sign-in` if missing, and redirects to `homeForRole(profile.role)` if the role doesn’t match.

### Configuration loading
Env vars are read via `process.env.*` directly (`NEXT_PUBLIC_*` at build **and** run time; server-only keys at run time). No custom config loader. `.env.local` is used in dev (see `.env.local.example`).

### Database connection
No pool/connection object is held. Each server render/action calls **`createClient()`** (`lib/supabase/server.ts`) which builds a per-request Supabase client from cookies; the browser uses `lib/supabase/client.ts`. RLS runs every query as the authenticated user.

### Middleware setup / route registration / service init
- Middleware = `proxy.ts` (see above). Routes = file-system based (App Router). No manual route registration.
- Realtime “service” is initialized by **`MessagingRealtimeProvider`** mounted once per shell layout (clinician/patient/parent layouts) — opens two Realtime channels for the signed-in user.

### Frontend initialization
Root layout → shell layout (`requireProfile` + parallel data fetch + sidebar/topbar + Realtime provider) → page (server component fetches via `data/*`) → interactive client components hydrate (canvas store created lazily via `useCanvasStoreInstance`, theme picked up post-hydration via `useSyncExternalStore`).

### Layouts
Root layout + one layout per route group. Shell layouts (`clinician`, `patient`, `parent`) enforce role via `requireProfile`, fetch notifications/unread counts/blueprint rules in parallel, and wrap children in the Realtime provider + sidebar/topbar. Full-screen routes are placed outside shells to own the viewport.

### State management
- **Canvas editor**: zustand vanilla store (`lib/canvas/store.ts`), one instance per editor mount (`useCanvasStoreInstance`), read via `useCanvasStore(store, selector)`. Holds width/height/background/pageStyle/elements/pages/pageIndex/selectedIds/dirty/past/future. Undo/redo with debounced checkpoints + explicit gesture bracketing (`beginGesture`/`endGesture`).
- **Realtime/messaging**: a lightweight pub/sub dispatcher (`lib/realtime/messaging-dispatcher.ts`) plus a React context for “which conversation is currently visible”.
- **Theme**: a tiny external store (`lib/theme.ts`) consumed via `useSyncExternalStore`.
- **Selected child (parent)**: a cookie (`lib/parent/selected-child.ts`), read on the server.
- Otherwise local component state + server-driven data (RSC).

### Hooks
`lib/canvas/use-fullscreen.ts`, `lib/canvas/store.ts` (`useCanvasStore*`), `lib/time/use-live-timestamp.ts`, theme subscribe hooks, `SpeakButton` uses `useSyncExternalStore`.

### API calls
- **Writes**: server actions imported directly into client components and awaited (no manual fetch). Auth forms use React 19 `useActionState` with the `ActionState` shape.
- **AI**: client `fetch('/api/ai/insights' | '/api/ai/worksheet', {method:'POST'})`.
- **Realtime**: browser Supabase client channel subscriptions.

### Forms & validation
Auth forms (`components/auth/*`) post to server actions; validation is server-side in `actions/auth.ts` (required fields, password ≥ 8, password match on reset). Many dialogs use `FormData`-based server actions. `react-hook-form`/`zod` are dependencies available for richer forms.

### Authentication flow (frontend)
Sign-up form (role-specific) → server action `signUpX` → Supabase `signUp` → (if session) redirect to role home (or `/…/creator-hub`/studio when `next=claim`). Sign-in → `signIn` action → role home or honored `redirect`. See §9.

### Routing
File-system App Router; route groups for layouts; dynamic segments `[templateId]`, `[patientId]`, `[assignmentId]`, `[clinicianPatientId]`. Proxy gates protected prefixes.

### UI structure & data movement
Server component fetches data (as the signed-in user, RLS-scoped) → passes props to client components → user interacts → client calls server action → action mutates via Supabase + `revalidatePath` → RSC re-renders with fresh data. For the canvas, the store is the single client-side truth; autosave serializes `toCanvas()` and calls `saveTemplateCanvas` with optimistic-concurrency checking.

## 7. Backend

### Server
Next.js server runtime (Node). No Express/Koa. “Controllers/services” map to **route handlers**, **server actions**, and **`data/*` fetchers**; business logic lives in pure libs (`scoring`, `review`, `goals`, `analytics`) and in **Postgres** (RLS + functions).

### Middleware
`proxy.ts` / `updateSession` (session refresh + auth gate). See §5.

### Authentication / Authorization / Validation
- AuthN: Supabase Auth (§9).
- AuthZ: **primarily RLS + `SECURITY DEFINER` functions** (§8/§9), with server actions adding ownership scoping (e.g. `submitAttempt` refuses an assignment not owned by the caller; `/api/ai/worksheet` enforces clinician role).
- Validation: server actions trim/coerce inputs and enforce limits (password length, repeat 1–30, MAX_ROWS 200, duration clamp ≤ 6h). DB `CHECK` constraints back critical invariants.

### Error handling / logging
Server actions return `{ error }`-shaped results (or `ActionState`) rather than throwing to the client; AI routes map failures to 4xx/5xx JSON. Server-side `console.error` for diagnostics (auth failures, proxy failure, notify failure). Route error boundaries: `app/error.tsx`, `app/global-error.tsx`. Notifications intentionally **swallow** failures so a failed ping never blocks the real action.

### Background processes
None (see §2). Recurring assignments materialized at creation.

### Major endpoints / actions

**Route handlers (addressable URLs):**

1. **`POST /api/ai/insights`** (`src/app/api/ai/insights/route.ts`)
   - Purpose: generate + cache an AI progress summary for one patient.
   - Auth: must be signed in (401 otherwise); the caller must be the treating clinician (looks up `clinician_patients` by `id` + `clinician_id = user.id`).
   - Request body: `{ clinicianPatientId: string }`.
   - Flow: validate → resolve patient link → load that clinician’s assignments for the patient → load up to 15 most-recent attempts → build `AttemptSummary[]` → `generateInsights()` (Claude) → insert into `ai_insights` → return saved row.
   - DB: `clinician_patients`, `assignments`, `activity_attempts`, `ai_insights`.
   - External: Anthropic.
   - Errors: 401 (not signed in), 400 (missing id / no assignments / no attempts), 404 (patient not linked), 500 (save failed), 502 (AI failed).

2. **`POST /api/ai/worksheet`** (`src/app/api/ai/worksheet/route.ts`)
   - Purpose: generate a printable worksheet template from a topic.
   - Auth: signed in **and** `profiles.role === 'clinician'` (403 otherwise) — explicitly hardened because the *route* (not just the page) is what an attacker calls, and it spends money + creates a template.
   - Request: `{ topic, domain?, instructions? }` (topic required).
   - Flow: `generateWorksheet()` (Claude) → `worksheetToCanvas()` → insert `templates` row (`medium:'print'`) → return `{ templateId }`.
   - DB: `profiles`, `templates`. External: Anthropic.
   - Errors: 401, 403, 400 (no topic), 500 (save), 502 (AI).

3. **`GET /auth/confirm`** (`src/app/auth/confirm/route.ts`)
   - Purpose: turn an email link’s one-time token into a session cookie, then redirect. Must be a route handler (a Server Component can’t set cookies).
   - Query: `token_hash`+`type` (stateless, preferred) **or** `code` (PKCE, same-browser only); `next` (open-redirect-guarded via `safeRedirect`, default `/reset-password`).
   - Flow: `verifyOtp` or `exchangeCodeForSession` → on failure redirect `/forgot-password?error=link` (specific cause logged only) → on success redirect to `next`.

**Server actions (representative — full list in §13):** `signIn`, `signUpClinician/Patient/Parent`, `requestPasswordReset`, `updatePassword`, `signOut`; `submitAttempt`, `claimInviteCode`; `createTemplateFromWizard`, `claimGuestDraft`, `createClinicianWorksheet`, `saveTemplateCanvas`, `updateTemplateMeta`, `setTemplateStatus`, `duplicate/delete/restore/purgeTemplate`, `setTemplateThumbnail`; `createAssignment`, `markAssignmentInProgress/Completed`; `getAttemptReview`, `setAttemptNote`; `invitePatient`, `archive/reactivatePatient`; messages (`sendMessage`, `startConversation`, `startParentConversation`, `markConversationRead`, `edit/deleteMessage`, `loadOlderMessages`); goals (`createGoal`, `setGoalStatus`, `deleteGoal`); billing (`issueInvoice`, `setInvoiceStatus`); library (`setTemplatePublic`, `importTemplate`, `publishAsset`, `deleteAsset`, `loadTemplatePreview`); parent (`claimGuardianCode`, `selectChild`, `createParentTemplate`, `setParentTemplateVisibility`, `deleteParentTemplate`, `assignTemplateToChild`, `saveWorksheet`, `removeSavedWorksheet`); notifications (`notify`, `markNotificationRead`, `markAllNotificationsRead`); blueprint rules (`addBlueprintRule`, `removeBlueprintRule`); `searchCommandPalette`.

## 8. Database

**Technology:** Supabase Postgres, `pgcrypto` extension, RLS enabled on every application table. Canvas documents are `jsonb`.

### Tables (verified from `supabase/migrations/*` and `types/database.ts`)

- **`profiles`** — one row per auth user. `id` (PK, FK → `auth.users`, ON DELETE CASCADE), `role` (`clinician|patient|parent`; original init allowed only clinician/patient, 0002 added `parent`), `full_name`, `email`, `avatar_color`, `headline`, `created_at`. Auto-created by trigger `handle_new_user` on `auth.users` insert (reads `role`/`full_name` from signup metadata).
- **`clinician_patients`** — caseload link + invite. `id` PK, `clinician_id` FK, `patient_id` FK (nullable until claimed), `display_name`, `invite_code` (unique — makes bearer *become* the patient), `guardian_code` (added 0002, unique — for parents, never grants patient access), `status` (`invited|active|archived`), `notes`, `created_at`.
- **`templates`** — authored activities. `id`, `owner_id` FK, `title`, `description`, `domain`, `medium` (`interactive|hybrid|print`), `status` (`draft|published|archived`), `canvas` (jsonb `TemplateCanvas`), `thumbnail_color`, `deleted_at` (soft delete), `is_public` (Global Library, distinct from `status`), `thumbnail_url` (nullable, added in migration 0013 — pointer to a creator-uploaded image in the `template-assets` bucket; `thumbnail_color` is the fallback), `created_at`, `updated_at` (bumped by `set_updated_at` trigger).
- **`assignments`** — a template assigned to a patient, with a frozen snapshot. `id`, `template_id` FK (ON DELETE SET NULL), `clinician_id` FK (nullable since 0003), `assigned_by` FK (0003, NOT NULL — who created it), `patient_id` FK, `title`, `instructions`, `due_date`, `status` (`assigned|in_progress|completed`), `canvas_snapshot` (jsonb), `created_at`.
- **`activity_attempts`** — a completed run. `id`, `assignment_id` FK (cascade), `patient_id` FK, `responses` (jsonb), `score` (numeric, **nullable** — null when nothing to mark), `correct_count`, `total_count`, `duration_seconds`, `clinician_note`, `completed_at`. **Unique index `activity_attempts_one_per_assignment` on `assignment_id`** (0012, conditional).
- **`ai_insights`** — cached Claude summaries. `id`, `patient_id`, `clinician_id`, `summary`, `strengths`/`concerns`/`recommendations` (jsonb arrays), `attempts_considered`, `generated_at`. Clinician-only (never shown to patient/parent).
- **`notifications`** — recipient-owned inbox. `id`, `user_id`, `type`, `title`, `body`, `link`, `reference_id` (polymorphic; for `new_message` = `conversation_id`), `read_at`, `created_at`. **Partial unique index `notifications_dedup_idx` (user_id, type, reference_id) WHERE read_at IS NULL** enables race-free upsert of message notifications.
- **`assets`** — Global Library standalone images. `id`, `owner_id`, `url`, `alt`, `created_at`. Public read, owner write.
- **`conversations`** — messenger. `id`, `clinician_patient_id` (nullable unique FK), `parent_child_id` (0002, nullable unique FK), `created_by`, `last_message_at`, `last_message_preview` (denormalized via trigger), `created_at`.
- **`conversation_participants`** — N-ary membership + per-user state. `id`, `conversation_id`, `user_id`, `joined_at`, `last_read_at`, `archived_at`, `pinned_at`, `muted_until`. Unique `(conversation_id, user_id)`.
- **`messages`** — `id`, `conversation_id`, `sender_id` (nullable, ON DELETE SET NULL), `message_type` (`TEXT|IMAGE|FILE|SYSTEM`, presentation-only), `body` (nullable), `metadata` (jsonb), `edited_at`, `deleted_at` (soft delete only), `created_at`. Trigger `messages_touch_conversation` keeps conversation preview fresh.
- **`patient_goals`** (0010) — `id`, `patient_id`, `clinician_id`, `title`, `domain` (nullable = all), `target_accuracy` (1–100, default 80), `window_attempts` (1–50, default 5), `status` (`active|achieved|archived`), `created_at`, `achieved_at`. CHECK: `(status='achieved') = (achieved_at is not null)`.
- **`blueprint_rules`** (0006) — shared authoring standards. `id`, `body` (1–500 chars, unique), `created_by`, `is_default`, `sort_order`, `created_at`. 15 seeded defaults (safety/privacy/clarity/accessibility/language). No UPDATE grant/policy (add-or-retire only); defaults can’t be deleted.

## 9. Authentication & Authorization

### Login
`signIn` action → `supabase.auth.signInWithPassword` → reads `profiles.role` (source of truth, not JWT) → redirect to `homeForRole(role)` or a `safeRedirect`-validated `?redirect=`.

### Signup
Role-specific actions (`signUpClinician/Patient/Parent`) call `supabase.auth.signUp` with `options.data = { role, full_name, ... }`. Trigger `handle_new_user` creates the `profiles` row. If email confirmation is **on**, `signUp` returns no session and the action tells the user to confirm (and that the invite/guardian code must be re-entered from the dashboard, since it can’t be claimed without a session). If **off**, patient/parent then `claim_invite`/`claim_guardian_code`.

### Sessions / tokens / cookies / JWT
Supabase JWT stored in cookies via `@supabase/ssr`. The proxy refreshes the session per request (`getUser()`), writing refreshed cookies onto the response. Server client reads cookies via `next/headers`; browser client via `createBrowserClient`. JWT carries a `role` metadata claim used only as a best-effort hint; the DB `profiles.role` is authoritative.

### Password handling
Supabase stores a one-way **bcrypt** hash; plaintext is never recoverable. Minimum length 8 enforced in every signup + the reset path. Reset flow: `requestPasswordReset` → `resetPasswordForEmail(redirectTo=<origin>/auth/confirm?next=/reset-password)`; `/auth/confirm` verifies the token and establishes a session; `updatePassword` (requires that session) calls `updateUser({password})`.

### OAuth
None (email/password only).

### Roles / permissions / protected routes
Roles: clinician, patient, parent. Route protection is two-layered: **proxy** (authenticated-or-not on `/clinician|/patient|/parent`) + **`requireProfile(role)`** on the page/layout (DB role must match, else redirect to that role’s home). The **real** permission boundary is **RLS**: e.g. patients can SELECT+INSERT their own attempts but cannot UPDATE/DELETE them (0008); a patient can only change an assignment’s `status` (0008 trigger); clinicians see their caseload’s data; guardians see their child’s (0002/0004); billing scoped by `can_bill` (0005); notifications only between linked parties (`can_notify`).

### Logout / expiration
`signOut` action → `supabase.auth.signOut()` → redirect `/`. Session expiry handled by Supabase; the reset link expiry surfaces as “that link expired” when `getUser()` is empty at `updatePassword`.

### Open-redirect protection
`safeRedirect()` (`lib/auth/redirects.ts`) allows only same-origin absolute paths (`/...`, not `//...`, not absolute URLs), shared by the sign-in `?redirect=` and the email-link `?next=`.

**Security note (verbatim intent from code):** passwords are non-recoverable by design; the app never attempts to read or crack them.

## 10. Complete Feature-by-Feature Explanation

Below, each feature is traced user action → frontend → action/API → DB/external → response → UI. (Element-level scoring rules are in §8/scoring; see `src/lib/scoring.ts`.)

### Feature: Template Studio (canvas authoring)
1. **What:** a drag-and-drop editor to build a multi-page therapy activity/worksheet.
2. **Why:** authoring digital equivalents of paper materials + interactive tasks.
3. **User flow:** Clinician → Studio → “Initialize” wizard (Medium → Foundation → Identity) → editor at `/clinician/studio/[templateId]`; drag elements from the palette, edit via properties panel, multi-page, undo/redo, autosave, publish.
4. **Frontend:** `canvas-editor.tsx`, `canvas-surface.tsx`, `element-box.tsx`, `properties-panel.tsx`, `editor-sidebar.tsx`, `page-bar.tsx`, `layers-panel.tsx`, `selection-toolbar.tsx`, store `lib/canvas/store.ts`.
5. **Backend:** `createTemplateFromWizard`, `saveTemplateCanvas` (optimistic concurrency via `updated_at`), `updateTemplateMeta`, `setTemplateStatus`, `setTemplateThumbnail`.
6. **DB:** `templates` (canvas jsonb; `set_updated_at` trigger).
7. **APIs/external:** image upload → Storage `template-assets`.
8. **Key functions:** store `addElement/updateElement/undo/redo/toCanvas`, `ELEMENT_LIBRARY` (defaults), `allPages`.
9. **Execution:** store holds live page; `toCanvas()` folds page 1 into `elements` and pages 2+ into `pages`; autosave posts serialized canvas.
10. **Errors/edge:** save conflict returns `{conflict:true}` (another tab/device changed the row); `force` overwrite. History debounced + gesture-bracketed.
11. **Design decisions:** page 1 stored flat for backward compat; per-element appearance not global; starters shipped as code not DB rows.

### Feature: Assignment (single, bulk, recurring)
- **What/Why:** push a published template to one/many patients, optionally repeated over days, snapshotting the canvas so later edits don’t change assigned work.
- **Flow:** assign dialog (single hidden patient field) or bulk (checkbox per patient) → `createAssignment`.
- **Backend:** `createAssignment` — validates repeat 1–30, every-N-days 1–30, requires due date when repeating, caps at 200 rows; `repeatDueDates()` steps UTC days; flat-maps patients × dates; one notification per patient.
- **DB:** `assignments` (snapshot = `template.canvas`), `notifications`.
- **AuthZ:** RLS `assignments_assigner_insert` requires `assigned_by=auth.uid()` AND `can_assign_to(patient)`.
- **Edge:** duplicate patient ids deduped; empty caseload path avoids bad revalidate.

### Feature: Activity Player + submit
- **What/Why:** patient completes an assigned activity full-screen; scored honestly server-side.
- **Flow:** `/patient/activity/[assignmentId]` → `activity-player.tsx` renders `element-player.tsx` per element, scales to fit (stacks below ~0.67 factor for phones), read-aloud via `speak-button`, progress counter → Submit → `submitAttempt`.
- **Backend:** `submitAttempt(assignmentId, {responses, durationSeconds})` — verifies ownership, refuses a second attempt (app check + `23505` unique-violation fallback), scores via `scoreCanvas(canvas_snapshot, responses)`, `score = total>0 ? round(correct/total*100) : null`, clamps duration ≤ 6h, marks assignment completed, notifies `assigned_by`.
- **DB:** `assignments` (read snapshot, set completed), `activity_attempts` (insert), `notifications`.
- **Design:** only `responses` trusted from client; marks computed on server; `null` score for unscorable activities.

### Feature: Per-question Attempt Review
- **What/Why:** clinician/guardian see, question by question, what was asked / answered / correct — including replayed drawings.
- **Flow:** open an attempt → `getAttemptReview(attemptId)` → `reviewCanvas(canvas_snapshot, responses)` → `attempt-review.tsx` (+ `ReviewDrawing` SVG replay).
- **DB:** `activity_attempts` join `assignments(title, canvas_snapshot)`; RLS scopes visibility (clinician/guardian select policies), so no extra auth check needed.

### Feature: Analytics & Clinical Pulse
- **What/Why:** accuracy over time, per-domain, caseload status, rankings.
- **Frontend:** `charts/progress-chart.tsx`, `clinician/analytics/*`, `clinician/pulse/*`, `clinician/report/*`.
- **Backend/data:** `data/clinician.ts` fetchers normalize rows to `AnalyticsAttempt`; `lib/analytics/*` compute `PatientAnalytics`/`CaseloadPulse`. Zero-`total` attempts are **not** accuracy-countable (single definition in `analytics/accuracy.ts`).
- **DB:** `activity_attempts` + joins to `assignments`/`templates(domain)`.

### Feature: Patient Goals
- **What/Why:** target accuracy over a window of recent attempts; judged only on a full window.
- **Backend:** `createGoal/setGoalStatus/deleteGoal`; pure `goalProgress()` (pooled over items, date-filtered from goal creation).
- **DB:** `patient_goals` (RLS: clinician writes, patient/guardian read).
- **UI:** `clinician/goals-card.tsx`, `goals/goal-progress-bar.tsx`, `goals-readonly.tsx` (also in printable report).

### Feature: AI Insights & AI Worksheet Generator
- **Insights:** clinician-only cached summary (`POST /api/ai/insights` → Claude → `ai_insights`). Trigger hidden entirely if no `ANTHROPIC_API_KEY`.
- **Worksheet gen:** clinician-only (`POST /api/ai/worksheet` → Claude → `worksheetToCanvas` → `templates`).

### Feature: Messaging (Realtime)
- **What/Why:** clinician↔patient and clinician↔parent threads (kept separate).
- **Flow:** `startConversation`/`startParentConversation` (get-or-create) → `sendMessage` → Realtime broadcasts to participants (RLS-scoped delivery) → dispatcher updates unread badges; `markConversationRead`, `edit/deleteMessage` (soft), `loadOlderMessages`.
- **DB:** `conversations`, `conversation_participants`, `messages`, `notifications` (`notify_new_message` upsert).
- **Frontend:** `MessagingRealtimeProvider` (per shell), `message-thread.tsx`, `conversation-list.tsx`, `messages-split-pane.tsx`.

### Feature: Notifications (Alert Hub)
- `notify()` wrapper → `create_notification` RPC (authorized by `can_notify`); `notification-bell.tsx`; Realtime on `notifications`; `markNotificationRead`/`markAllNotificationsRead`.

### Feature: Global Library (publish/import, public browse)
- Publish a template (`setTemplatePublic`) / asset (`publishAsset`); import (`importTemplate`) copies into your library; public pages under `(marketing)/library/*`; starters are code and served specially (`starter__`-prefixed ids). RLS `templates_public_select` allows anon read of `is_public && !deleted`.

### Feature: Parent / Guardian area
- Link via guardian code (`claimGuardianCode`); child selector (cookie); missions/progress/calendar; author printable worksheets (`createParentTemplate`, public by default) and assign to own child (`assignTemplateToChild`); save worksheets; read-only finances. RLS grants parents read of their children’s records (0002) and clinicians read of their patients’ guardians (0005).

### Feature: Guest “Try” Studio
- `/try` (outside all shells) → `GuestStudio` builds a worksheet in `localStorage`; on sign-up `claimGuestDraft` converts it into a real `templates` row (`next=claim` routing).

### Feature: Billing / Invoices (record only)
- `issueInvoice` (scoped by `can_bill`), `setInvoiceStatus`; parent sees non-draft invoices. **No card processing.**

### Feature: Print / PDF
- `print/assignment/[assignmentId]`, `print/template/[templateId]`, clinician report print; `components/print/printable-canvas.tsx` renders the canvas at authored size with print CSS.

### Feature: Blueprint Rules
- Shared authoring standards; readable by all signed-in users, clinician-writable, 15 seeded defaults (undeletable). `addBlueprintRule`/`removeBlueprintRule`; shown in the Studio dialog.

### Feature: Command Palette
- `searchCommandPalette(query)` + `command-palette/command-palette.tsx` for quick navigation/search.

## 12. Data Flow

**Write (patient completes an activity):**
```
Patient taps answers (element-player)
 → activity-player collects Responses (client)
 → submitAttempt(assignmentId, {responses, durationSeconds})   [server action]
   → createClient() (RLS as patient)
   → read assignments (ownership + canvas_snapshot)
   → check no existing attempt (+ DB unique index backstop)
   → scoreCanvas(canvas_snapshot, responses)   [pure, server]
   → insert activity_attempts (correct/total/score)
   → update assignment status=completed
   → notify(assigned_by)
   → revalidatePath(/patient …)
 → returns {score,correct,total}
 → player shows results screen
```

**Read (clinician views a patient):**
```
requireProfile('clinician')  → data/clinician.ts fetchers (RLS-scoped)
 → normalize rows → AnalyticsAttempt[] → lib/analytics/* → PatientAnalytics
 → server component passes to clinician/analytics + report components → charts
```

**Canvas edit:** UI event → zustand action (`updateElement` …) → store state → autosave serializes `toCanvas()` → `saveTemplateCanvas` (optimistic concurrency) → `templates.canvas` (+ `updated_at` trigger).

**Realtime message:** `sendMessage` → `messages` insert (+ trigger updates conversation + `notify_new_message`) → Supabase Realtime broadcasts (RLS per subscriber) → browser dispatcher → unread badge / thread update.

## 18. Error Handling

- **How errors are generated:** validation in server actions; Supabase/PostgREST errors; DB CHECK/unique violations (e.g. `23505`); Claude/network failures; RLS denials (rows simply don’t appear).
- **Propagation:** server actions return `{error}`/`ActionState` (not thrown) so client UIs can render messages inline; AI route handlers map to HTTP status codes + JSON.
- **User-facing:** friendly messages (e.g. “You’ve already finished this activity.”, “Set a due date — repeats are spaced out from it.”, neutral password-reset message to avoid account enumeration). Route error boundaries (`app/error.tsx` with digest, `app/global-error.tsx`).
- **Logging:** `console.error` with `[context]` prefixes (auth, proxy, notify, data fetchers). No external log service.
- **Retry:** no automatic retries in app code (the deploy guidance mentions retry-with-backoff for git push only). Optimistic-concurrency conflict on save is surfaced for the user to retry/force.
- **Fallback:** proxy fails **open**; notifications fail **silently**; AI JSON parse falls back to raw text (insights) or a “try again” error (worksheet); unknown OTP types redirect to a friendly page.

## 19. Security

**Implemented (verified):**
- **RLS on every application table** is the primary boundary; server actions add ownership scoping on top.
- **`SECURITY DEFINER` functions** with pinned `search_path` for privileged operations, each doing its own authorization check (`claim_invite`, `create_notification`, `can_notify`, `can_bill`, `can_assign_to`, etc.).
- **EXECUTE revoked from PUBLIC** for definer/trigger functions (0009 fixed the no-op revokes in 0007/0008); only app-called functions granted back to `authenticated`.
- **Server-side scoring** (`submitAttempt`) — client cannot forge scores; only `responses` is trusted.
- **Attempt records locked** (0008): patients can’t UPDATE/DELETE attempts; column grant limits clinician updates to `clinician_note`; a trigger restricts patients to changing only assignment `status`.
- **One-attempt-per-assignment** enforced in DB (0012) + app.
- **Open-redirect guard** (`safeRedirect`) on both redirect entry points.
- **Account-enumeration mitigations** on password reset (neutral message; 429 is the only exception, logged).
- **AI worksheet route hardened** to clinicians (route-level, not just page-level).
- **Storage** writes scoped to `<uid>/…`.
- **Passwords** bcrypt (Supabase); min length 8; never recoverable; app never attempts recovery.
- **Guardian vs invite code separation** so a parent can’t become the patient.

**Areas worth reviewing (observations, not exploited):**
- **Realtime no-filter assumption** (`messaging-provider.tsx`): message delivery relies entirely on `messages_participant_select` RLS being enforced per-subscriber by Realtime; the code comment says this was **not empirically verified** against a live project and prescribes a manual test. Worth confirming.
- **Email confirmation off** (README suggests disabling for local dev) means sign-up leaks “User already registered” — a known, documented limitation in `actions/auth.ts` comments.
- **SMTP / password-reset delivery** and **leaked-password protection** are operational Supabase settings (noted in dev history as pending) — verify in the dashboard.
- `next.config.ts` sets **no explicit security headers/CSP** (relies on platform defaults).
- The README’s **stale migration list** could lead an operator to skip 0007–0013, leaving notifications/lockdowns/thumbnails unapplied — apply all 13.
- **Do not** hardcode or expose `NEXT_PUBLIC_*` beyond what’s intended (anon key is public by design; service-role keys must never be added client-side — none are used here).

## 20. Performance

Supported by code:
- **DB indexes** on all hot paths (FKs, `messages(conversation_id, created_at)`, `notifications(user_id, created_at desc)`, partial public/dedup/one-attempt indexes).
- **Denormalized** `conversations.last_message_at/preview` (trigger) so inboxes don’t aggregate messages per render.
- **Lazy per-question review**: `canvas_snapshot`s are loaded on demand (opening one attempt), not shipped with the attempt list.
- **AI insights capped** at 15 attempts per prompt.
- **Assignment cap** (200 rows) prevents runaway bulk inserts.
- **Canvas history** capped at 50 snapshots; checkpoints debounced (500ms) + gesture-bracketed to avoid per-event churn.
- **Parallel data fetches** in shell layouts (`Promise.all`).
- **RSC** keeps heavy rendering server-side; **optimistic concurrency** avoids clobbering saves.
- **Realtime reconnect reconciliation** in the provider (postgres_changes is fire-and-forget).

Potential bottlenecks (observations): large canvases are stored/serialized whole in `templates.canvas`/`assignments.canvas_snapshot` (jsonb) — big multi-page activities move a lot of JSON; the `properties-panel.tsx` (3098 lines) and `element-player.tsx` (2732 lines) are large client bundles for the editor/player routes. No image resizing/CDN transform pipeline beyond Supabase Storage. No server response caching layer (relies on RSC + `revalidatePath`).

## 24. Things That Are Easy to Miss

- **Middleware is `src/proxy.ts`, not `middleware.ts`** — Next 16 renamed it. Also `export const config.matcher`.
- **The proxy does NOT enforce role-vs-route** (only authenticated-or-not). Role routing is owned by `requireProfile` on the page. This split is deliberate to avoid redirect loops.
- **Authorization lives in Postgres (RLS + definer functions)**, not just in TypeScript. Reading only the server actions will under-count the security model.
- **`profiles.role` is the source of truth**, not the JWT role claim (they can drift).
- **Canvas page 1 is stored flat** (`canvas.elements` / `canvas.pageStyle`); pages 2+ live in `canvas.pages`. Use `allPages()` — reading `.elements` alone silently ignores later pages (a bug scoring once had).
- **Scoring is server-side and item-based**; a `total` of 0 means “not scored” (score `null`), not 0% — and `formatAttemptResult` prints “Not scored”.
- **`assigned_by` vs `clinician_id`** on assignments: parent-assigned work has `clinician_id = null`; visibility for the treating clinician is by `is_clinician_of(patient)`, not by who created the row.
- **Two codes per caseload row**: `invite_code` (become the patient) vs `guardian_code` (guardian access) — never interchangeable.
- **Starters/blueprints are code**, not DB rows; `starter__`-prefixed ids route to code, and ids must not be renamed (URL-safe on purpose).
- **Notifications never block actions** (errors swallowed by design).
- **Recurring assignments are materialized up front** — no scheduler exists.
- **`can_notify` had to learn parent↔child** (0011) — a subtle relationship gap that silently dropped notifications.
- **The `0009` lesson**: `revoke … from anon` does nothing if the privilege comes via PUBLIC; you must `revoke … from public`.
- **AI insights trigger is hidden entirely** when `ANTHROPIC_API_KEY` is unset (not a broken button).

## 25. How to Modify the Project Safely

- **Adding a new element type:** update `types/canvas.ts` (add to the union + `INTERACTIVE_TYPES` if scored), add defaults/palette entry in `lib/canvas/defaults.ts`, a properties editor in `properties-panel.tsx`, a play-time renderer in `element-player.tsx`, a preview in `element-preview.tsx`, a scoring case in `lib/scoring.ts` (+ tests in `scoring.test.ts`), and a review case in `lib/review.ts`. Keep new fields **optional** so old canvases still parse.
- **Adding a new role shell:** add prefix to `ROLE_ROUTE_PREFIXES` (`lib/auth/roles.ts`) **and** `homeForRole`, create the route group + layout with `requireProfile`, and add RLS. Missing the prefix leaves the area ungated at the proxy (this exact bug happened with `/parent`).
- **Changing the schema:** write a new idempotent migration (`… if not exists`, `drop policy if exists … create policy`), update `types/database.ts` by hand, and add/adjust RLS. Prove policies against a local Postgres acting as the target role (rolled-back transactions), as the existing migrations do.
- **Touching scoring/analytics/goals:** they’re pure and tested — change the lib + its test together; the UI must **render** these models, never recompute.
- **Autosave/canvas store:** preserve the page-1-flat serialization (`toCanvas`) and gesture bracketing; respect optimistic concurrency in `saveTemplateCanvas`.
- **Realtime:** don’t add a real `DELETE` path to `messages`/`notifications` (RLS can’t scope deletes in Realtime — soft-delete only). Re-audit unread-count components before enabling `cacheComponents`.
- **What breaks what:** editing `types/canvas.ts` ripples to scoring/review/player/editor; editing RLS/functions can silently hide or expose rows; renaming starter ids breaks bookmarked preview/print links.
- **Testing changes:** `npm test` (unit), `npm run lint`, `npm run build`; for anything user-facing, drive it in a browser (the project’s stated QA method) and re-check RLS for new tables.
- **Conventions:** long explanatory comments over TODOs; server actions return `{error}` (don’t throw to client); trim/validate inputs server-side; keep new canvas fields optional.

## 27. Beginner Explanation

Imagine a speech therapist who normally works with printed worksheets and flashcards. **Verbal Coach** lets them build those activities on a computer instead — like making slides — then send them to a child to do at home, and automatically see how the child did.

- The therapist logs in and opens the **Studio**. They drag pieces onto a page: a question, four pictures, a matching game, a tracing box. They press save (it saves by itself) and “publish”.
- They add a child to their **caseload**, which gives them a secret **invite code**. The child (or their parent) makes an account with that code, which links them together. There’s a *separate* code for parents so a parent can watch without becoming the child.
- The therapist **assigns** an activity — to one child, or many, or the same one every day for a week.
- The child opens it in a big, friendly **player**. They tap answers, and a **speaker button** can read the question out loud for kids who can’t read yet. When they finish, the app **grades it on the server** (not on the child’s device, so the score can’t be faked) and shows a happy results screen.
- The therapist then sees **charts** of accuracy over time, can open any attempt and see **exactly which questions** were right or wrong (even replaying a child’s drawing), sets **goals** (“80% on articulation over 5 activities”), and can ask an **AI** to write a short progress summary.
- **Parents** get their own view of their child’s progress, can send home-practice worksheets, and can message the therapist. There’s also a **billing** list (just record-keeping — no real payments).

Under the hood: the website is built with **Next.js** (pages + server code in one app). All the data lives in **Supabase** (a hosted Postgres database with login built in). The clever part is that the **database itself enforces who can see and change what** (called Row Level Security), so even if someone tried to cheat by calling the server directly, the database refuses. The **AI** parts use Anthropic’s Claude and are optional.

How the parts connect: your browser shows the pages → when you do something, it calls a small server function → that function talks to the database *as you* (so the rules apply) → the page updates. Messages and alerts arrive live over a websocket.

## 28. Glossary

- **Template** — an authored activity/worksheet (a canvas document) owned by a clinician (or parent).
- **Canvas / `TemplateCanvas`** — the JSON document (`width, height, background, elements[], pages?`) describing an activity.
- **Element** — one item on the canvas; ~44 types across *content* (text/image/shape/…), *interactive* (scored: multipleChoice, dragMatch, wordSearch, drawPad, …), and *worksheet* (static print furniture: table, checklist, letterBoxes, …).
- **Interactive type** — an element that is scored (`INTERACTIVE_TYPES`).
- **Assignment** — a template given to a patient, with a **frozen `canvas_snapshot`** so later edits don’t change assigned work.
- **Attempt (`activity_attempts`)** — a patient’s completed run; stores responses + server-computed score.
- **Snapshot** — the copy of the canvas taken at assign time.
- **Partial credit / item-based scoring** — score by items correct within an element, not all-or-nothing.
- **“Not scored” / `total = 0`** — an activity with nothing to mark (drawings, stories); score is `null`, not 0%.
- **Invite code** — links a patient account to a clinician (bearer *becomes* the patient).
- **Guardian code** — a separate code linking a parent to a child (guardian access, never patient access).
- **RLS (Row Level Security)** — Postgres per-row access rules; the real authorization layer.
- **SECURITY DEFINER function** — a DB function running with its owner’s privileges, doing its own auth check (bypasses RLS safely for a narrow purpose).
- **Blueprint** — a starter canvas layout (code) a clinician can start from.
- **Blueprint rule** — a shared authoring *standard* (text), seeded defaults + clinician additions.
